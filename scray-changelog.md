# Scray audio change log

Reasoning history for code changes. Git holds *what* changed; this holds *why*.
Same convention as the other Scray repos (see the top of scray-browse's `scray-changelog.md`):
one entry per edit, newest first, written in the same commit as the `VERSION` bump,
named `test:` until it has been tried and then `stable:`. Record the reasoning, not the diff.

## Entries

### audio 1.7 — test: easier sign-in and go-to fixes
<!-- 2026-10-14T11:40Z -->
- **Why:** (1) the app's sign-in sheet was clunky: its styles (`.sa-*`) were never written, so it showed as a bare form at the bottom of the page, and it asked for everything at once. (2) "Go to album" / "Go to artist" misbehaved. When a track has no album-artist tag, the server uses the track's own artist as the album artist, so a compilation splits into one-track "albums", and "Go to album" opened just that one track.
- **What:** `app.js` signs in the way Scray Native does (`scray-device-key.js`): password first, the authenticator-code box only once the server asks, six digits submit by themselves, a recovery-code link, the library address tucked behind "change", "Later" lasts until the app is next opened. Styles added to `audio.css`. The Offline panel gets Sign in / Sign out (the app only; sign-out also tells the server, using the page's own dialog because the web view has no `confirm`). "Go to album" now opens "this album tag in this folder" (`#/album/<artist>/<album>/<folder>`), titled "Various artists" when the tracks disagree; the album link under a track name does the same. Going to the page you are already on re-runs it instead of doing nothing. An untagged track no longer offers "Go to artist: Unknown artist". `api.php` and `offline.js` sort an album read by folder the same way as one read by artist (kept in step).
- **Tested:** `tests/ui_navigate.py` (new, Playwright, by hand): split compilation, accents, same-page, untagged track, and the sign-in flow against a pretend `device_pair`. `smoke.py`, `ui_offline.py` pass.
- **Not changed:** artist pages are still keyed by album artist, so on a split compilation each track's artist still has its own page. Grouping by folder in the Albums/Artists lists would need a different rule; say if you want it.

### audio 1.5 — test: BBW Sounds iOS app
<!-- 2026-10-13T21:15Z -->
- **Asked:** adapt the library into an iOS app, as a workflow that outputs an IPA, that can save files offline, kept in a folder like Scray Native's; named BBW Sounds. (The page and server half is audio 1.4.)
- **Built like scray-native, on purpose:** Expo SDK 57 / RN 0.86 with one Swift module, `expo prebuild` + `xcodebuild` on `macos-latest`, unsigned IPA, optional publish to the same SideStore source (`scripts/sidestore-publish.js`, copied). Bundle id `com.mac.scrayaudio` (SideStore adds the team id after it), version `1.0.<run number>`. In `app/`, so the site's deploy never serves it (`.htaccess` blocks `/app/`).
- **The page is bundled, not loaded from the site.** The app has to open with no network (that is the point of offline), so `make-web.js` turns `index.php` into a static `index.html` (PHP login check and cache numbers dropped, the site-only `/scray/` scripts removed) and the build copies it into the app, as Native does with `assets/web`. Cost: a page change needs a new IPA. A "Remote" variant that loads the page from a staging folder, as Native has, is the obvious follow-up if that gets tiresome.
- **Swift, kept small:** `ScrayAudioView` (web view + bridge), `ScrayAudioStore` (picked folder as a security-scoped bookmark, held open for the app's life like Native's `BookmarkStore`; paths joined onto `Offline/` and never out of it), `ScrayAudioDownloads` (URLSession download task, throttled progress, screen kept on while saving, a background-task grace), `ScrayAudioSchemeHandler` (`scray-audio://local/…`, Range support, chunks read off the main thread, a stopped task never written to - the same shape as Native's 13.180 video handler). Playing a saved track is not a bridge call: the page points `<audio>` at that URL.
- **Background audio:** `UIBackgroundModes: audio`, and the audio session is given the `playback` category at launch but only *activated* by WebKit when something plays, so opening the app doesn't stop other music. Lock-screen controls come from the page's Media Session.
- **Icon: original, not the one offered.** The BBC Sounds logo was sent as the icon; I don't make app icons from another organisation's logo, so this is a drawn teal disc with a pair of notes on dark (`app/assets/icon.png`, 1024×1024 RGB, no alpha). Swap `app/assets/icon.png` for your own art at any time. The name is BBW Sounds (display name; the page's header says it too).
- **The build workflow can't be debugged from here by reading logs** (the runner's log storage isn't reachable from this session), so it writes the interesting lines of a failed build out as an annotation, and its last check opens the finished `.app` and fails the build if the page files, the display name or the audio background mode are missing. That is how the first Swift errors (two optional-to-`NSNull` replies) were found and fixed.
- **Checked:** the macOS build compiles and packages an IPA; the IPA check passes (page files, display name BBW Sounds, bundle id, background mode). **Not tried, and I can't from here:** the app on a real iPhone. In particular: the folder picker, a real download to the chosen folder, playback from `scray-audio://` (WebKit's handling of a custom scheme for `<audio>` is the piece I'd watch), background and lock-screen playback, the sign-in against the real `device_pair`, and the covers' signed links from a `file://` page. The browser test already covers the page side of all of these with a pretend app.
- Needs from you: copy the `SIDESTORE_*` secrets into this repo if you want builds published; set the `AUDIO_URL` variable (or type the address into the sign-in sheet); first install via SideStore from the run's artifact or the source.

### audio 1.4 — test: offline filter and save offline
<!-- 2026-10-13T20:54Z -->
- **Asked:** an iOS app that can save files to the phone, with an "offline" filter in the interface that shows only what is downloaded, kept in a folder like Scray Native's. This is the page and server half; the app itself is audio 1.5.
- **Saved files live where Native's do:** `<picked folder>/Offline/<the track's library path>`, covers in `Offline/.covers/` (one per folder, not one per track). The page keeps the list of what is saved (`offline.js`) and writes it to a small file in that folder through the app, so it survives a reinstall; a file deleted in the Files app drops out of the list at the next start.
- **The Offline filter has no server to ask, so it is the server's browse logic re-done in the page** (`createLocal`: ls, tracks, artists, albums, genres, search, stats). The risk of a second copy is that it drifts, so `tests/offline-parity.js` (in the smoke test, so in CI) loads every track and checks the local answers equal api.php's for every folder, artist, album, genre and a set of searches, including accents and `%`. It passed first time, but on a 6-track library: add odd names to the test library when one turns up.
- **A saved track always plays from the phone** (`scray-audio://local/...`), whether or not Offline is on. Offline mode off shows the whole library; with no connection, or signed out, the page switches to Offline on its own and says so.
- **Server:** `shapeTrack` now returns `path` and `size` (the app needs them to save under the right name and to total up a selection before asking). New `cover_url` returns a signed cover link as JSON, because an `<img>` in the app can't send the key header. CORS headers and an `OPTIONS` answer, because the app's page is not on the site's origin.
- **Phone keys (a security decision, so stated plainly):** `api.php` now also accepts Scray's per-phone keys (`sd_` + 64 hex), checked by hash against `scray-data/scray_devices.json`, the file Scray's `device_pair` / twofactor.php already manage. A phone signed out there stops working here. It only reads the file; it never writes it. CORS is `*`, which is safe here because nothing rides on cookies from another site: a page on another origin has no key to send. A phone key gets browse, playlists and the scan button - the same as a session - and not the scanner's `audio_worker_*` actions (tested).
- **In the page:** a sign-in sheet (`app.js`: library address, password, authenticator code, phone name), Save / Remove from offline in the track menu and a **⤓ Offline** menu on albums, folders and so on, a size and free-space question before saving several, a downloads panel (progress, cancel, retry, chosen folder), saved rows marked ⤓, covers fetched through signed links a few at a time as they scroll into view. Up to 3 downloads run at once.
- **Checked:** `tests/smoke.py` (phone key accepted, unknown key refused, phone key refused on worker actions, CORS preflight, `cover_url`, `path` / `size`, offline parity). `tests/ui_offline.py` drives Chromium with a pretend app behind the page, from another origin with a phone key: save one (file at the right path, cover saved once, manifest written), the filter on folders / artists / search, play from the phone, restart keeps the list, server unreachable switches to Offline, save a whole album (asks, shows the count) and remove it (files and cover deleted). The earlier scan and playlist UI tests still pass. **Not tried:** a real iPhone, the real Swift side (that is 1.5), and a real Hostinger deploy.
- Deploy: redeploy `staging` on Hostinger. Nothing changes on the gateway. Browsers see no difference (the Offline controls stay hidden outside the app).

### audio 1.3 — test: playlists and track menu
<!-- 2026-10-13T20:34Z -->
- **Asked:** playlists that live on the server, and a right-click menu on each track that goes to the album and artist.
- **Playlists are in the same SQLite file as the library** (schema version 3: `playlists`, `playlist_items`), so they follow the login, not the browser. An item is one *place* in a playlist (its own id), so a track can be in a list twice and Move / Remove act on that place, not on every copy. Items point at `tracks.id`: a rescan keeps a path's id, so tag changes and renames of the tags are harmless; a file moved to a new path is a new track and drops out. Those are hidden from the list but counted (“N tracks no longer in the library”) with a one-click clear, rather than silently vanishing or being matched by guesswork. Names are unique ignoring case and accents (folded in PHP, since SQLite's NOCASE is ASCII-only). Limits: 100-character names, 50,000 tracks a playlist.
- **API:** `playlists`, `playlist`, `playlist_create` (optionally with tracks), `playlist_rename`, `playlist_delete`, `playlist_add`, `playlist_remove` (by entry, or all missing), `playlist_move` (before another entry, or to the end). Same tier as browsing (session or console key); the scanner's key can't touch them. Moving is “put this before that” rather than “go to position n”, so hidden missing items can't throw the positions off.
- **The menu:** one floating menu for right-click, the new **⋯** button on every row (right-click doesn't exist on iOS), the queue rows and the now-playing strip. Items: Play, Play next, Add to queue, Go to album, Go to artist, More by (only when the track artist differs from the album artist: artist pages are keyed by album artist, so this searches instead of pointing at a page that may not exist), Show in folder, Add to playlist ›. It is a sheet at the bottom on a phone. Keyboard: arrows, Home/End, Enter, Escape; the player's shortcuts don't fire behind it. Adding to a playlist swaps the menu's contents (with a Back item) instead of opening a side submenu, which works on touch.
- **Adding in bulk:** a **＋ Playlist** button next to Play / Shuffle on albums, folders, artists, genres and search; it uses the same list that Play uses, so what you'd hear is what gets added.
- **A small in-page dialog** (name entry, delete confirmation) instead of the browser's `prompt()`/`confirm()`: those are blocking, look wrong on iOS, and can't be styled.
- **Two older bugs fixed on the way:** the track-list heading always had five column names, so on album pages (which hide Artist and Album) Time wrapped onto a second line; and `show()` passed `null` straight to `replaceChildren`, which writes the word “null” into the page (it did on the Albums page).
- **Checked:** `tests/smoke.py` (about 100 checks) covers every playlist action, auth, duplicates, ordering, a track leaving the library, and delete. Headless Chromium at desktop and phone width: right-click, ⋯, Escape, Go to album / artist / More by, create from a track, add a whole album, duplicate name refused, the Playlists page, move up / down, remove one copy, rename, delete with Cancel and confirm, menu on the queue and now-playing strip, the phone sheet, no sideways scroll, no page errors, no native dialogs. **Not tried:** the real Hostinger deploy and mobile Safari (long-press, the sheet's safe-area spacing).
- Deploy: redeploy `staging` on Hostinger (the database upgrades itself). Nothing changes on the gateway.

### audio 1.2 — test: scan button
<!-- 2026-10-13T20:26Z -->
- **Asked:** a button in the page that starts a scan, and live scan progress in the app, so the scanner doesn't have to be run by hand.
- **Why it goes through a request, not a direct start:** the scanner lives on the gateway and Hostinger can't reach in and run it. So the button only writes a request into the database (`meta.scan_requested_at`). A second small unit on the gateway, `scray-audio-scan-poll` (every 30 s), asks `api.php` whether there is one and, if so, runs `systemctl start --no-block scray-audio-scan.service`. Starting the real service rather than scanning inside the poller means systemd itself prevents two scans at once, and the nightly timer and the button can't collide. The cost is up to 30 s before it starts; the panel says so while it waits. The poller runs as root because starting a service needs it; all it reads from `api.php` is one yes/no.
- **One click, one scan:** `audio_worker_poll` takes the request (clears it and records a claim), so a request is used once. Pressing the button while a scan runs, or in the short window between the gateway taking a request and the scan starting, does nothing.
- **Progress:** the scanner reports folders, files seen, tags read and errors to `audio_worker_progress` at most every 2 s (and after each batch); a failed report never stops the scan. The page reads `scan_status` every 2 s while the panel is open or a scan is active, once a minute otherwise (so the nightly scan still shows), and not at all in a hidden tab. The bar is a real percentage against the size of the last complete scan, and a sliding bar when there isn't one yet.
- **It can say when something is wrong, instead of spinning:** a scan with no update for 5 minutes is shown as stopped (the scanner crashed or the gateway went away); a request nobody has picked up, with no check-in from the poller for 2 minutes, shows the command to turn the timer on; a scan that ends on an error records why (`stopped: ...`).
- **Database:** schema version 2 adds progress columns to `scans` and a `meta` table. It upgrades an existing database in place on the first request.
- **Checked:** `tests/smoke.py` (now about 70 checks) covers the request / take / start / progress / finish cycle, one-click-one-scan, scan during scan, a stale scan, a failed scan, `--poll` with and without a request, and a failing start command. Headless Chromium at desktop and phone width: open the panel, press the button, waiting / starting / running (live counts, percentage, spinning header button) / finished (toast, refresh button), Escape, no sideways scroll, no page errors. **Not tried:** the real systemd units and a real Hostinger deploy.
- Deploy: redeploy `staging` on Hostinger (the database upgrades itself); on the gateway copy the new `scray-audio-scan.py` to `/opt/scray/` and the two new `scray-audio-scan-poll.*` files to `/etc/systemd/system/`, then `systemctl daemon-reload && systemctl enable --now scray-audio-scan-poll.timer`.

### audio 1.1 — test: scanner base64 bodies
<!-- 2026-10-13T20:18Z -->
- **Asked:** the first full scan stopped at about 1,400 files with a plain-text `403 Forbidden` from `audio_worker_seen`.
- **Why I think it happened:** api.php never answers in plain text (it always sends JSON), so the 403 came from in front of PHP, most likely Hostinger's web firewall inspecting the request body. The body held file paths, and one path probably matched a rule (names with `../`, `select ... from`, `<`, and so on). The same call worked on the earlier batches, which fits a single odd file name. Not confirmed: I haven't seen which file it was.
- **Fix:** the scanner now sends every payload base64-encoded (`X-Scray-Enc: b64`, `text/plain`) and api.php decodes it before reading the JSON. A firewall has nothing to match on in base64. Plain JSON bodies are still accepted. The `..` path-segment check in api.php is unchanged.
- **Checked:** `tests/smoke.py` now posts a path containing `x../select * from x/<b>.mp3` in base64, and a plain body, and the scanner itself runs through the base64 path. All pass. **Not tried:** the real firewall, so whether this clears the 403 is only known once the full scan is re-run.
- Deploy: this changes `api.php` (Hostinger) and `gateway/scray-audio-scan.py` (copy to `/opt/scray/` on the gateway).

### audio 1.0 — test: first cut
<!-- 2026-10-13T19:54Z -->
- **Asked:** a simple web interface, desktop and mobile browser, to browse (by folder or by metadata), play and shuffle the mp3 and flac files in `/home/audio` on the Hetzner box; borrow as much of Scray's infrastructure as possible.
- **What's borrowed, and why it matters:** nothing here invents auth or streaming. Login and 2FA are Scray's own (`scray_auth.php`, `/scray/login.php`); `api.php` accepts a session or the console key, the way `rebuild.php` does. Playback uses the gateway's `secure_link` links with the same recipe as `scrayHetznerUrl()` (decoded path hashed, one space before the secret), on a new `/a/` route so the audio read-only sub-account and the video one stay separate. Secrets stay in `scray_secrets.php`; only `audio_worker_key` is new.
- **Tags come from a scanner on the gateway, not from PHP.** mutagen reads mp3 and flac tags reliably and the VM can read the box directly; doing it in PHP on shared hosting would have meant pulling the first part of every file through Hostinger. The scanner reads only the front of each file (ID3 size / FLAC metadata blocks tell it how much) and only for files that are new or whose etag changed, so a nightly rescan is mostly folder listings. A read-only sub-account can't list folders, so the scanner uses a second one with read-only off; the streaming one stays read-only.
- **MP3 length:** without a Xing header mutagen divides the bytes it was given (only the front), which would give a wrong length. The scanner uses the real file size for a constant-rate file. Checked with a file written without Xing.
- **Albums are grouped by album artist** (falling back to artist, then "Unknown artist"), so a compilation is one album, not one per track artist.
- **Search folds accents and case** into a stored column (SQLite's LIKE only handles ASCII), so "edith" finds "Édith". Artists and albums are filtered the same way in PHP.
- **The scan can't empty the library:** it only removes what it didn't see after a complete walk; a partial walk (`SCRAY_SCAN_ROOT` / `SCRAY_SCAN_MAX`), an empty one, or one that would remove more than half the tracks removes nothing.
- **The player:** one `<audio>` element. iOS only lets an element play without a tap once a tap has started it, and the real track arrives after a network round trip, so the first tap starts it with a silent clip and the real source is swapped in. A link that expires mid-pause or mid-play is re-signed and resumed from the same second. Media Session gives lock-screen controls. Three failed tracks in a row stop the queue instead of racing through it.
- **Checked:** `tests/smoke.py` (fake box and gateway, the real api.php and scanner): auth, scanning and rescans, folder / artist / album / genre / search results, signed links (signature, Range, forged link refused, names with accents, `&` and `'`), cover redirect, prune safety, re-reading a changed file. Headless Chromium against the page: browsing, real playback, next / previous / seek / auto-advance, queue, shuffle, repeat, search, phone width with no sideways scroll. **Not tried:** the real `scray_auth.php` (a stand-in is used), the real gateway, Hostinger, and mobile Safari.
- **Watch:** the first tap in Safari on a phone is the thing to test (unlock + background play + lock screen). Embedded cover art, saved queues and gapless playback are not here yet.
- Deploy: the whole repo through Hostinger git; `audio_worker_key` in `scray_secrets.php`; the gateway `/a/` route and the scanner (README, "Setting it up").
